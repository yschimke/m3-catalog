## What "ready" means

- The shell in `src/main/kotlin/ee/schimke/m3catalog/uid/` has the hand-written sticker's
  function name, parameters and annotations, verbatim, so it publishes the same preview ids.
- Its body is a generated component (`build/generated/uid/kotlin`), exported by the UI builder's
  own exporter from `stickers/<name>.uid` plus that document's cells. The generated code holds no
  catalog helper: copy is string resources, knobs and click counters come in as parameters.
- `compare-local.py` found every capture identical.

## Cutting over

1. **Release the upstream changes** the export needs, then point `uidExportVersion` /
   `screenModelVersion` at the releases and drop the Maven-local snapshots:
   - compose-ai-tools: components-only output (#5883, in 2.51.0); a components file's opt-ins
     once (#5885, merged) and toggle intents with empty optional slots (#5896): the next release
     after both;
   - compose-ui-builder: string resources (#729, merged, in the 3.109.0 release PR) and #732
     (intent callbacks, colour bundles, outlines, enum and state vocabulary, toggle shapes, and
     `exportComponents` on compose-ai-tools 2.51.0): the release after it merges, once its
     tools pin moves to the release carrying #5896.
2. **Move the published inventory:** for each ready sticker, delete the hand-written function
   from `:catalog`'s `sections/` and publish `:uid-stickers` in its place (it is already a
   preview module with the same ids). The shells keep the catalog's meta-annotations working
   through `composePreview.componentLibraryPrefixes`.
3. **Keep the gate:** run `compare-local.py` in CI against the previous delivery's renders for
   every migrated sticker, so a document edit or an exporter release that changes a pixel is
   caught where the hand-written diff used to catch it.
4. The blocked stickers stay hand-written until the exporter grows their vocabulary; the
   refusal for each is in the table above and in `blocked/<name>.json`.
